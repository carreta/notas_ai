# TD-009 — LLM provider and model strategy

## Status

Proposed

## Context

The application requires an LLM provider and model capable of analyzing meeting content and producing structured results.

The decision must balance output quality, structured-response support, latency, cost, reliability, privacy, and the ability to change providers or models as the project evolves.

Affected decisions:
- TD-002 — AI application contract.
- TD-003 — AI timeout budget.
- TD-004 — Synchronous request vs queue/job processing.
- TD-005 — Retry/re-analysis behavior.
- TD-006 — Result persistence.
- TD-010 — Priority extraction/inference policy.
- TD-011 — Relative due-date representation/resolution.

## Constraints

- The selected model must support the required context size for the defined meeting input limits.
- The provider must support structured output or provide a reliable mechanism for validating structured responses.
- Cost must be compatible with the project's expected usage.
- Latency must be acceptable for the selected processing strategy.
- Provider-specific integration should remain isolated from the application layer.
- The architecture should allow the provider/model to be changed without rewriting the application workflow.

## Options considered

### Option A — Single managed commercial LLM provider

Select one commercial provider and one primary model for Phase 2.

**Pros:**
- Fastest path to implementation.
- Mature APIs and tooling.
- Predictable operational model.
- Access to high-quality general-purpose models.

**Cons:**
- Vendor dependency.
- Provider outages affect the application.
- Pricing may change.
- Migration to another provider requires adapter work.

### Option B — Multi-provider abstraction from the start

Implement the AI port so multiple providers/models can be configured and used interchangeably.

**Pros:**
- Reduced vendor lock-in.
- Easier provider fallback.
- Allows cost/quality comparisons.
- Supports future provider diversification.

**Cons:**
- Higher initial complexity.
- Different providers may expose different capabilities.
- Requires more adapters and integration tests.
- Can delay Phase 2 implementation.

### Option C — Self-hosted/open-weight model

Run an open-weight LLM using project-controlled infrastructure.

**Pros:**
- Greater control over data and infrastructure.
- No per-request external API dependency.
- Potentially predictable long-term operating costs at sufficient scale.
- Provider independence.

**Cons:**
- Significant infrastructure and operational requirements.
- Model hosting and scaling become project responsibilities.
- Hardware costs can be substantial.
- Quality/latency may not match managed models for the target workload.

### Option D — Primary provider with provider-independent application port

Select one provider/model for Phase 2 while implementing the application boundary through the provider-independent interface defined in TD-002.

**Pros:**
- Fast implementation while preserving architectural flexibility.
- Provider-specific code remains isolated.
- Easier future provider replacement.
- Avoids premature multi-provider infrastructure.
- Enables realistic evaluation using the selected model.

**Cons:**
- Still introduces an initial provider dependency.
- A second provider requires a new adapter later.
- Fallback between providers is not available initially.

## Decision

Elegimos la opcioon d combinada con la c, queremos implementar un proveedor principal (OpenAI) junto con una arquitectura que permita la adicion de provedores y modelos en el futuro, pero al mismo tiempo queremos utilizar modelos locales para la depuracion durante el desarrollo o para el cliente.
