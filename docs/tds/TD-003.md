# TD-003 — AI timeout budget

## Status

Approved

## Context

AI analysis introduces external processing latency that can vary depending on meeting size, provider, model, network conditions, and service availability.

The application needs a defined timeout budget to prevent AI requests from occupying application resources indefinitely and to establish predictable behavior for users and downstream workflows.

Affected decisions:
- TD-002 — AI application contract.
- TD-004 — Synchronous request vs queue/job processing.
- TD-005 — Retry/re-analysis behavior.
- TD-009 — LLM provider/model strategy.

## Constraints

- AI requests must have a finite timeout.
- The timeout must account for the expected latency of the selected provider/model.
- Timeout behavior must produce a distinguishable application-level failure.
- The timeout must not cause uncontrolled retries or duplicate analysis.
- The chosen strategy must be testable without relying on actual provider delays.
- If asynchronous processing is selected, the timeout must distinguish request timeout from job execution timeout.

## Options considered

### Option A — Fixed global timeout

Use a single timeout value for all AI analysis requests.

**Pros:**
- Simple to configure and understand.
- Easy to test.
- Predictable behavior across providers.

**Cons:**
- Different providers/models may have different latency characteristics.
- Large meetings may require more processing time.
- A single value may be unnecessarily restrictive for some models or unnecessarily long for others.

### Option B — Provider/model-specific timeout

Configure the timeout according to the selected provider and model.

**Pros:**
- Better aligned with actual provider characteristics.
- Allows optimization for latency and reliability.
- Supports different model capabilities.

**Cons:**
- More configuration complexity.
- Requires provider/model-specific operational knowledge.
- Changing providers may require configuration changes.

### Option C — Layered timeout budget

Define an overall application timeout plus lower-level provider/network timeouts.

**Pros:**
- Provides an upper bound for the entire operation.
- Allows individual infrastructure layers to fail earlier.
- Better control over failure propagation.
- Suitable for both synchronous and asynchronous architectures.

**Cons:**
- More complex to configure.
- Requires clear ownership of each timeout.
- Can be harder to diagnose if timeout values are poorly coordinated.

## Decision

The team selected **Option A — Fixed global timeout**. All AI analysis requests use a single fixed global timeout of **120 seconds**. The timeout applies to the AI analysis operation. Exceeding the timeout produces the application-level `AI_TIMEOUT` failure and is never treated as a success or partial success. The value may be revisited later using real production or provider performance measurements.

## Consequences

### Positive

- Simple configuration and easy to understand.
- Deterministic behavior across providers and models.
- Easy to test, including simulated timeouts without real waits.
- Provides an upper bound on synchronous AI processing time.

### Negative

- Some slow or large requests may time out.
- A single value may not suit every provider or model.
- Synchronous workers may remain occupied for up to 120 seconds.
- Future operational evidence may justify provider/model-specific timeout values.

## Compatibility / migration

- No database migration is required.
- Provider HTTP clients/adapters must apply the 120-second timeout.
- Tests should simulate timeout behavior without waiting 120 real seconds.
- The timeout value may be exposed via configuration.
- Changing the timeout later should not require changing the application result contract.
