# TD-014 — GitHub merge strategy

## Status

Proposed

## Context

The project needs a consistent strategy for integrating pull requests into the main branch. The merge strategy should preserve a useful project history while keeping the workflow simple for a small development team. 

## Constraints

- Pull requests must pass the required CI checks before being merged.
- Pull requests should receive code review before integration.
- The merge strategy should be consistent across the repository.
- The resulting main history should remain understandable and useful for debugging.
- The strategy should work well with short-lived feature branches for trunk-based integration.

## Options considered

### Option A: Squash merge

Pros 
- Keeps the Git history clean and organized.
- Combines an entire PR into a single commit.
- Makes it easy to revert a complete feature.
- Avoids unhelpful commits such as fix, change, correction.
- Simple to use for teams with limited Git experience.

cons
- The individual commit details are lost in the main branch.
- It is more difficult to analyze how a feature evolved internally.
- It reduces traceability at the individual commit level.
- If a PR is too large, it ends up being represented by a single large commit.

### Option B: Merge commit

Pros 

- Preserves all original commits.
- Provides complete traceability.
- Makes it possible to see how a feature evolved over time.
- Clearly maintains separation between different branches and PRs.

cons.
- The history can become cluttered and difficult to read.
- Creates additional commits such as Merge pull request....
- Preserves unnecessary commits 
- In projects with many PRs, the history can grow quickly.
- It can be more difficult to visually follow the evolution of main.


### Option C: Rebase merge

Pros 

- Produces a linear and clean history.
- Preserves individual commits.
- Does not create additional merge commits.
- Makes it easier to follow changes chronologically.
- Combines some of the traceability of Merge Commit with the cleanliness of Squash Merge.

cons.
- More complex to understand than Squash Merge.
- Rebase can generate conflicts that must be resolved correctly.
- Rewrites the commit history.
- Commit hashes may change.
- Can cause errors if the team does not fully understand how rebase works.
- Requires greater familiarity with Git.

## Decision

We chose Squash Merge because it keeps the Git history cleaner, more organized, and easier to understand. When a Pull Request is merged, all its commits are combined into a single commit, avoiding small or unnecessary commits in the main branch.

It also improves traceability, since each commit represents a specific feature or Pull Request. Additionally, it makes it easier to revert changes if a feature causes problems.

## Consequences

### Positive
- main remains easy to read and navigate.
- Each commit in main corresponds approximately to one completed pull request/change.
- Intermediate development commits do not clutter the project's permanent history.
- The resulting history is well aligned with a small-team trunk-based workflow.

### Negative
- Detailed information about the evolution of a change must be obtained from the pull request rather than the Git history.
- A poorly scoped pull request can result in a large, overly broad commit.
- Developers need to write meaningful pull request titles/descriptions because the squashed commit becomes the primary historical representation of the change.
