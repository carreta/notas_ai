# TD-006 — Normalized result tables vs JSON/hybrid persistence

## Status

Proposed

## Context

AI analysis produces structured results such as summaries, actions, priorities, due dates, and potentially other analysis metadata.

The system needs to determine how these results should be persisted so they can support future querying, UI presentation, history, and evolution of the AI contract.

Affected decisions:
- TD-002 — AI application contract.
- TD-004 — Synchronous request vs queue/job processing.
- TD-009 — LLM provider/model strategy.
- TD-010 — Priority extraction/inference policy.
- TD-011 — Relative due-date representation/resolution.

## Constraints

- Persisted analysis must remain associated with its source meeting.
- Important fields required by the application should be queryable.
- AI provider-specific response structures should not become the application's persistence contract.
- The schema should support future AI contract evolution.
- Persistence must preserve enough information to reproduce or inspect an analysis result when required.

## Options considered

### Option A — Fully normalized relational tables

Store analysis results and their components in dedicated relational tables.

**Pros:**
- Strong schema and referential integrity.
- Excellent queryability.
- Easy to index and filter structured fields.
- Clear relationships between meetings, analyses, actions, and other entities.

**Cons:**
- More tables and migrations.
- More complex persistence logic.
- AI schema changes may require database migrations.
- Potentially excessive for fields that are rarely queried.

### Option B — Store the complete result as JSON

Persist the AI analysis as a JSON document associated with the meeting.

**Pros:**
- Flexible schema.
- Easy to persist evolving AI output.
- Minimal migration requirements.
- Closely represents structured AI responses.

**Cons:**
- Weaker relational constraints.
- More difficult to query and index consistently.
- Application logic must interpret JSON structures.
- Data integrity can become dependent on application validation.

### Option C — Hybrid persistence

Store frequently queried/core business fields in normalized columns/tables while retaining the complete structured AI result as JSON.

**Pros:**
- Balances queryability and flexibility.
- Preserves the original structured result.
- Core application concepts can have strong relational constraints.
- AI output can evolve without requiring every provider/schema change to become a migration.

**Cons:**
- More complex than either pure approach.
- Some information exists in both structured and JSON representations.
- Requires clear ownership of canonical fields.
- Requires synchronization rules between normalized data and stored AI output.

## Decision

We chose Option C — Hybrid persistence. Core application data will be stored in normalized relational tables, while the complete AI analysis result will also be stored in a `jsonb` field for flexible access and easier handling of structured data.

## Consequences

### Positive

- Core business data remains structured and easy to query.
- The complete AI response is preserved without requiring schema changes for every result variation.
- `jsonb` provides flexible access to structured analysis data.
- The approach balances data integrity with flexibility.

### Negative

- The persistence model is more complex than using only relational tables or only JSON.
- The canonical source of duplicated data must be clearly defined.
- Changes to the AI result structure may require updates to application mapping and validation logic.

## Compatibility / migration

New normalized tables and/or relationships will be created for core analysis data if not present. The complete analysis result will be stored in a PostgreSQL `jsonb` column. No migration of existing analysis data is currently required.
