# TD-010 — Priority extraction and inference policy

## Status

Approved

## Context

AI analysis may identify actions, tasks, or follow-ups that appear to have different levels of importance or urgency.

The system needs to define whether priority should be explicitly extracted from meeting content, inferred by the AI, assigned using deterministic application rules, or left unspecified when the meeting does not provide enough information.

Affected decisions:
- TD-002 — AI application contract.
- TD-006 — Result persistence.
- TD-009 — LLM provider/model strategy.
- TD-011 — Relative due-date representation/resolution.

## Constraints

- The system must distinguish information explicitly stated in the meeting from AI inference.
- The AI must not represent uncertain priority assessments as factual statements.
- Priority values must use a controlled set of application-defined values.
- The policy must be deterministic enough to test.
- Missing or ambiguous priority information must have defined behavior.

## Options considered

### Option A — Explicit extraction only

Only assign a priority when the meeting explicitly provides enough information to determine it.

**Pros:**
- Minimizes unsupported AI inference.
- Easier to explain and audit.
- Lower risk of incorrect prioritization.
- Simple validation.

**Cons:**
- Many actions may remain without priority.
- Less useful when urgency is implied rather than explicitly stated.
- Requires the UI/application to handle unknown priority.

### Option B — AI inference

Allow the AI to infer priority from context, language, deadlines, dependencies, and other meeting signals.

**Pros:**
- Produces richer analysis.
- Can identify implied urgency.
- Reduces the number of actions without priority.

**Cons:**
- Higher risk of incorrect interpretation.
- Results may be subjective.
- More difficult to test deterministically.
- Requires clear confidence/uncertainty handling.

### Option C — Hybrid explicit extraction with constrained inference

Prefer explicitly stated priority information but allow AI inference according to defined rules when sufficient contextual evidence exists.

**Pros:**
- Balances accuracy and usefulness.
- Preserves explicit meeting information as the strongest signal.
- Allows inference where context is strong.
- Can define clear fallback behavior for ambiguous cases.

**Cons:**
- More complex policy.
- Requires clear rules for when inference is allowed.
- Inferred values may still be incorrect.
- Requires more comprehensive evaluation/testing.

## Decision

We chose Option C — Hybrid explicit extraction with constrained inference. The system will prioritize priority information explicitly stated in the meeting. When priority is not explicitly provided, the AI may infer it from sufficient contextual information.

Any inferred priority must be clearly indicated to the user.

## Consequences

### Positive

- Explicit meeting information remains the primary source of truth.
- The system can provide useful priorities when they are strongly implied by context.
- Users can distinguish inferred priorities from explicitly stated ones.
- The approach balances accuracy with usefulness.

### Negative

- Inferred priorities may still be incorrect.
- The system requires clear rules for when inference is allowed.
- UI and result types must represent whether a priority was explicit or inferred.
- Additional testing is required for ambiguous cases.

## Application priority contract

The approved policy (Option C — Hybrid explicit extraction with constrained inference) is reflected in the following application-owned result representation.

### Controlled priority values

- `LOW`
- `MEDIUM`
- `HIGH`
- `null` — allowed when there is not enough information to assign a priority.

Any value outside `LOW` / `MEDIUM` / `HIGH` is invalid structured output.

### Priority provenance values

- `EXPLICIT` — priority was explicitly stated in the meeting.
- `INFERRED` — priority was inferred from sufficiently supported context.

### Application-owned representation (inside action items)

- `priority: string|null`
- `priority_source: string|null`

### Rules

- Explicit priority information takes precedence over inference.
- Inference is allowed only when sufficiently supported by meeting context.
- An inferred priority must use `priority_source = INFERRED`.
- An explicitly stated priority must use `priority_source = EXPLICIT`.
- If `priority` is `null`, `priority_source` must also be `null`.
- Unsupported or ambiguous priority must not be fabricated.
- Any value outside `LOW` / `MEDIUM` / `HIGH` is rejected during validation.

These fields are scoped to `action_items` unless a separate approved decision requires otherwise.

## Compatibility / migration

The AI result contract and persistence model must include metadata indicating whether a priority was explicitly extracted or inferred. UI components must display this distinction to the user. Existing data does not require migration at this stage.
