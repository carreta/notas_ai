# TD-012 — Static-analysis tool/level

## Status

Proposed

## Context

Static analysis is intended to detect type-related defects, invalid assumptions, dead code, incorrect method calls, and other issues before runtime. Because the application relies heavily on Laravel conventions and APIs, the selected static-analysis configuration should understand Laravel-specific behavior, particularly Eloquent models, relationships, collections, facades, dependency injection, and framework helpers.

The decision therefore has two dimensions:

1. Which static-analysis tool should be used?
2. How strict should the analysis be during development and CI?

## Constraints

- The tool must support PHP and integrate well with Laravel and be executable locally and in CI.
- The initial configuration should not require developers to spend disproportionate effort resolving framework-related false positives.
- The configuration should be reproducible across developers and CI.
- The selected level should provide meaningful defect detection without blocking normal development unnecessarily.

## Options considered for level

### Option A: Minimum level

**Pros:**
- Low initial adoption cost and lower risk of slowing down early feature development.
- Faster onboarding for developers unfamiliar with static analysis.
- Fewer false positives and framework-related issues.

---

**Cons:**
- Many incorrect assumptions can remain undetected.
- Provides less protection against nullability, incorrect types, and invalid method/property access.
- Technical debt can accumulate in areas that are not covered by the initial configuration.

### Option B: Strict Level

**Pros:**
- Provides stronger guarantees about type correctness and detects more defects before runtime.
- Encourages explicit types, dependency contracts, and cleaner APIs.
- Prevents new code from introducing a large amount of type-related technical debt.

---

**Cons:**
- Higher initial setup and adoption cost, not to mention more annotations and explicit type definitions may be required.
- Developers may spend time satisfying the analyzer rather than addressing higher-value problems.
- Upgrading framework or dependencies can occasionally require updates to analysis configuration.

## Options considered for tools

### Option A: PHPStan

**Pros:**
- Speed Faster
- Maximum customization with 10 levels of strictness
- Fast execution, particularly when used with an appropriate configuration and result cache.

---

**Cons:**
- Limited knowledge of Laravel
- Eloquent casts are limited
- Eloquent may generate false positives
- Some framework-specific type information may not be available to PHPStan without Laravel-specific tooling

### Option B: Larastan

**Pros:**
- Works very well with Laravel.
- Better understanding of Laravel Collections types and generics
- Reduces false positives caused by Laravel's dynamic features
---

**Cons:**
- High memory usage
- May require PHPDoc/generics for complex code
- Analysis can become slower as the project and number of analyzed classes grow.

## Decision

Choose Larastan as the static-analysis tool and start at an intermediate level rather than immediately enforcing the strictest possible level. Because the application is Laravel-based and relies on framework behavior that plain PHPStan cannot understand as effectively without additional configuration.

The project will initially configure Larastan at a moderate analysis level that provides meaningful type checking while keeping framework-related friction manageable.The team should prioritize fixing genuine type/design problems over suppressing warnings. 

## Consequences

### Positive

- Laravel-specific code receives better static analysis and it becomes part of the normal development and CI workflow.
- Eloquent-related issues are more likely to be detected correctly.
- The team gets stronger guarantees about types and contracts without requiring excessive annotations from day one.
- Developers receive feedback before code reaches integration or production.

### Negative

- Larastan increases memory usage compared with a minimal PHPStan setup and CI execution time may increase as the project grows.
- Some Laravel behavior may still require configuration or explicit annotations.
- Developers will need to address static-analysis failures as part of normal development.
- Increasing strictness later may require some refactoring of existing code.
