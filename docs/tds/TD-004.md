# TD-004 — Synchronous request vs queue/job processing

## Status

Proposed

## Context

AI analysis may take significantly longer than normal application requests, particularly for large meeting transcripts or complex models.

The application needs to determine whether AI analysis should execute during the original HTTP request or be dispatched as an asynchronous background job.

Affected decisions:
- TD-002 — AI application contract.
- TD-003 — AI timeout budget.
- TD-005 — Retry/re-analysis behavior.
- TD-006 — Result persistence.
- TD-009 — LLM provider/model strategy.

## Constraints

- The system must provide predictable behavior when AI processing takes longer than expected.
- AI failures must not corrupt or invalidate the original meeting record.
- The architecture should support retries or re-analysis if required by TD-005.
- The user must be able to determine whether analysis is pending, successful, or failed.
- The solution should remain manageable for Phase 2 infrastructure.

## Options considered

### Option A — Synchronous AI analysis

Perform AI analysis within the same HTTP request that creates or submits the meeting.

**Pros:**
- Simple request/response flow.
- Immediate result available to the caller.
- Fewer infrastructure components.
- Easier initial implementation.

**Cons:**
- Request duration depends on AI provider latency.
- Greater risk of HTTP timeout.
- Poorer user experience for long meetings.
- Retries can be difficult to manage safely.
- Application workers remain occupied during AI processing.

### Option B — Asynchronous queue/job processing

Persist the meeting first and dispatch an AI analysis job to a queue.

**Pros:**
- Decouples meeting creation from AI latency.
- Better resilience to slow or temporarily unavailable providers.
- Natural support for retries.
- Workers can process AI analysis independently.
- Easier to expose pending/failed/completed analysis states.

**Cons:**
- Requires queue infrastructure.
- Adds state management and operational complexity.
- Results are not immediately available.
- Requires additional testing for asynchronous workflows.

### Option C — Hybrid strategy

Use synchronous processing for small/fast requests and asynchronous processing when configured thresholds are exceeded.

**Pros:**
- Can provide immediate results for simple cases.
- Avoids long synchronous requests for larger analyses.
- Allows gradual adoption of asynchronous infrastructure.

**Cons:**
- More complex application behavior.
- Different execution paths need to be maintained and tested.
- User experience becomes less predictable.
- Threshold selection adds additional configuration.

## Decision

Elegimos la A, por simplicidad de control de eventos.
