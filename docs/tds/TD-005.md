# TD-005 — Retry and re-analysis behavior

## Status

Proposed

## Context

AI analysis depends on an external provider and may fail due to transient network errors, provider availability, rate limits, timeouts, invalid responses, or other recoverable conditions.

The system needs to define when an analysis should be retried automatically and when a user or application action should explicitly request a new analysis.

The decision is particularly relevant if asynchronous processing is selected in TD-004.

Affected decisions:
- TD-002 — AI application contract.
- TD-003 — AI timeout budget.
- TD-004 — Synchronous request vs queue/job processing.
- TD-009 — LLM provider/model strategy.

## Constraints

- The system must avoid infinite retry loops.
- Retries must distinguish transient failures from permanent failures.
- Duplicate analysis must not create inconsistent or unintended results.
- Provider rate limits must be respected.
- Re-analysis must have predictable persistence behavior.
- Failures must remain observable for debugging and user feedback.

## Options considered

### Option A — No automatic retry; manual re-analysis only

Any AI failure is recorded and requires an explicit user/application action to retry.

**Pros:**
- Simple behavior.
- No unexpected additional provider costs.
- Easy to reason about.
- Avoids automatic retry loops.

**Cons:**
- Transient failures require user intervention.
- Poorer resilience to temporary provider/network issues.
- More manual operational work.

### Option B — Limited automatic retry

Retry recoverable failures a fixed number of times with backoff.

**Pros:**
- Handles transient failures automatically.
- Improves reliability.
- Can reduce unnecessary user intervention.
- Works naturally with queue-based processing.

**Cons:**
- Can increase provider costs.
- Requires classification of retryable failures.
- Adds implementation and testing complexity.

### Option C — Automatic retry plus explicit re-analysis

Use bounded automatic retries for transient failures while allowing users to explicitly request a new analysis.

**Pros:**
- Handles common transient failures automatically.
- Provides recovery for persistent failures.
- Gives users control over deliberate re-analysis.
- Supports operational recovery without hiding failures.

**Cons:**
- Most complex option.
- Requires clear distinction between retry and re-analysis.
- Requires idempotency/versioning rules.
- Can increase provider usage.

## Decision

La opcion hibrida entre la a y la b, donde se intenta automaticamente cierta cantidad de veces y si falla entonces muestra el boton de intentar.
