# TD-008 — Development/CI database engine

## Status

Proposed

## Context

The application requires a database engine for local development and CI environments.

The primary goals are to provide a development environment that is easy for contributors to reproduce, behaves consistently in CI, integrates well with Laravel, and minimizes differences between development/testing and the eventual production environment.

The database is also expected to persist structured meeting-analysis data such as meetings, participants, decisions, action items, priorities, due dates, and potentially raw or semi-structured AI output.

For this exercise, database choice should prioritize developer parity, CI simplicity, Laravel support, and predictable relational behavior over scalability requirements that are not currently established.

## Constraints

- The database must have strong Laravel support through Laravel's database abstraction layer and migrations.
- Developers should be able to run the application and its test suite with minimal environment-specific configuration.
- CI must be able to provision the database deterministically and run migrations/tests reliably.
- The selected engine should support the relational nature of the core domain.
- The solution should support structured querying for entities such as meetings, decisions, action items, participants, priorities, and due dates.

## Options considered

### Option A: PostgresSQL

**Pros:**
- Excellent fit for the relational nature of the application.
- First-class support through Laravel's database layer, migrations, Eloquent, and testing ecosystem.
- Provides JSON/JSONB capabilities, allowing structured relational data and flexible AI-generated metadata to coexist.
- Easy to run locally using Docker and straightforward to provision in CI.
Widely used in production environments, making developer/production parity easy to achieve.
- Mature ecosystem and extensive documentation.

---

**Cons:**
- Requires a running database service for local development and CI, unlike an embedded database such as SQLite.
- Slightly more operational setup than a lightweight embedded database.

### Option B: TiDB

**Pros:**
- MySQL-compatible relational database with horizontal scalability capabilities.
- Can provide familiar SQL semantics for applications already targeting MySQL-compatible systems.
- Distributed architecture can support large-scale workloads.
- Compatible with many existing MySQL tools and application patterns.

---

**Cons:**
- Distributed scalability is unnecessary for the current scope of the project.
- Less conventional choice for a small Laravel application than PostgreSQL or MySQL.
- CI and local development may require more infrastructure and configuration than PostgreSQL.
- Choosing it primarily for future scalability would constitute premature optimization.

### Option C: MongoDB Atlas

**Pros:**
- Document-oriented model can represent raw or semi-structured AI output naturally.
- Flexible schema can accommodate changes to AI-generated result structures.
- Managed Atlas infrastructure can reduce operational work for a hosted MongoDB deployment.
- Useful when the application's primary data model is inherently document-oriented or highly variable.

---

**Cons:**
- The core domain is strongly relational: meetings have participants, decisions, action items, due dates, etc.
- Relationships and referential integrity are less natural than in PostgreSQL.
- Would introduce a second conceptual model compared with Laravel's typical relational application architecture.
- MongoDB Atlas is a cloud service rather than simply a database engine, which introduces unnecessary infrastructure coupling for this decision.

## Decision

We choose PostgreSQL for development and CI. PostgreSQL provides the best balance between developer parity, CI simplicity, Laravel integration, relational modeling, and future production suitability. Not to mention most of the application's core entities and relationships are naturally relational, while PostgreSQL's JSON/JSONB capabilities provide sufficient flexibility for storing semi-structured AI output or metadata where appropriate.

## Consequences

**Positive**
- Development and CI can use the same database engine as production, reducing environment drift.
- Laravel integration remains straightforward and well supported.
- Relational constraints can enforce important domain invariants.
- Transactions provide reliable behavior for multi-step persistence operations.
JSON/JSONB allows flexible storage for raw AI responses or metadata without requiring a document database.
**Negative**
- Local development requires a PostgreSQL service/container.
- CI setup is slightly more involved than using an embedded database.
