# TD-001 — Maximum meeting text length

## Status

Proposed

## Context

The system needs to define a maximum size for meeting text submitted for AI analysis. Without an application-level limit, very large meeting transcripts may increase processing cost and latency or exceed the context limits of the selected AI provider/model.

The decision must also avoid coupling the application's input validation directly to a specific AI provider or model, since the provider/model selection is handled separately by TD-009. The solution should distinguish between the maximum meeting input accepted by the application and the token budget available to the AI analysis pipeline.

Affected decisions:

- TD-001: Maximum meeting text length.
- TD-002: AI application contract.
- TD-009: AI provider/model selection.

## Constraints

- The application must enforce a predictable maximum size for meeting submissions.
- The application-level limit must not depend directly on the selected AI provider or model.
- AI processing must respect the context/token limitations of the selected provider and model.
- The exact AI token budget may be determined or adjusted after TD-009 is resolved.
- Inputs exceeding the application-level limit must be rejected rather than silently truncated.

## Options considered

### Option A — Fixed character limit

Pros:

- Simple to implement and validate.
- Easy to communicate to users.
- Deterministic and independent of the AI provider.
- Straightforward to test.

---

Cons:

- Characters do not map directly to tokens.
- A valid input could still exceed the AI model's context limit.
- Does not directly account for AI processing cost.

### Option B — Fixed word limit

Pros:

- Easy for users to understand.
- Provides an approximate indication of transcript size.
- Independent of the AI provider.

Cons:

- Words do not map directly to tokens.
- More difficult to validate consistently.
- Formatting, timestamps, code, and other content can significantly affect token consumption.
- Does not guarantee compatibility with the selected model's context window.

### Option C — Token-based input limit

Pros:

- Closely represents the actual constraint relevant to AI processing.
- Better suited for controlling model context, latency, and cost.
- Directly compatible with AI provider limitations.

Cons:

- More complex to calculate and validate.
- Tokenization may depend on the selected model/provider.
- Couples application input validation more closely to AI infrastructure.
- Less intuitive for users.

### Option D — Character input limit with AI token budget

Pros:

- Provides simple and deterministic application-level validation, while also providing token budget for multiple models.
- Allows the AI integration to enforce model-specific context and token constraints.
- Makes it possible to change providers/models without changing the application's fundamental input contract.
- Provides a path for future chunking or other long-input processing strategies.

Cons:

- Requires two different limits to be defined and documented
- Requires additional logic for token estimation/validation.
- Exact AI token limits may need to change when the provider/model changes.

## Decision

Option D is accepted, the application will enforce a product-level maximum meeting text length based on characters, while enforcing a model/provider-compatible token budget. The exact character limit and token budget will be established according to the AI provider/model selected in TD-009, preliminary limits can be imposed for development porpuses.

The system must reject meeting submissions that exceed the application-level character limit or token window, while providing an understandable message to the user. Future implementations may introduce chunking, summarization, or another long-input strategy if required, but those mechanisms are outside the scope of this decision.

## Consequences

### Positive

- Meeting input validation can enforce model-specific context and token constraints.
- Provider/model changes do not inherently require changing the application's meeting input contract.
- Input limits are deterministic and straightforward for users and developers.
- Cost and context management remain responsibilities of the AI integration layer.

### Negative

- The system must maintain and document multiple different limits.
- Validation requires token-budget management.
- Future chunking or summarization may be required for larger meetings.

### Testing / operations / team workflow

Tests should cover:

- Meeting text below the maximum character limit.
- Meeting text exactly at the maximum.
- Meeting text exceeding the maximum.
- Meeting text that approach or exceed the configured token budget.
- Correct rejection/handling when the validation cannot fit within the model's context.
- Provider/model-specific token configuration once TD-009 is resolved.

## Compatibility / migration

The meeting submission contract should include the configured maximum text length and token budget as a validation constraint.

Changing the application-level character limit in the future may require updating validation rules, documentation, frontend constraints, and related tests, but should not require a database migration unless the database column itself imposes a stricter limit.
