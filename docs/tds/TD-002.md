# TD-002 — Exact AI port/interface and application result types

## Status

Proposed

## Context

The application needs a stable contract between the application layer and the AI analysis implementation. The contract must define how meeting data is submitted for analysis and how the resulting analysis is represented to the rest of the application.

The decision affects the AI integration architecture, application services, result persistence, validation, testing, and future provider implementations.

Affected decisions:
- TD-002 — AI application contract.
- TD-009 — LLM provider/model strategy.
- TD-006 — Result persistence strategy.
- TD-010 — Priority extraction/inference policy.
- TD-011 — Relative due-date representation/resolution.

## Constraints

- The application must not depend directly on a specific LLM provider SDK.
- The interface must support replacing or adding AI providers without changing the application workflow.
- Application result types must be deterministic enough to validate and test.
- The contract must represent successful results and relevant failure cases.
- The contract must support structured analysis results required by downstream persistence and UI.
- Provider-specific request/response formats must remain outside the application contract.

## Options considered

### Option A — Application service with provider-independent DTOs

Define an application-level analysis service/port using explicit request and result DTOs.

**Pros:**
- Strong separation between application logic and AI providers.
- Easy to mock and test.
- Explicit input/output contract.
- Provider implementation can change without affecting consumers.
- Suitable for structured result validation.

**Cons:**
- Requires additional DTO/interface definitions.
- Requires mapping between provider responses and application types.
- More initial design work.

### Option B — Provider SDK response exposed to the application

Allow the application service to return the provider's native response structure.

**Pros:**
- Less initial code.
- Minimal mapping between provider response and application.
- Easy to access provider-specific capabilities.

**Cons:**
- Strong coupling to the selected provider.
- Provider changes can require changes throughout the application.
- More difficult to test independently.
- Provider-specific structures leak into persistence and UI layers.
- Makes multiple-provider support more difficult.

### Option C — Generic untyped/loosely typed result

Return a generic array/object containing the analysis result.

**Pros:**
- Flexible during early development.
- Minimal upfront schema design.
- Easy to accommodate provider-specific fields.

**Cons:**
- Weak contract between layers.
- Errors may only be detected at runtime.
- More difficult to validate and test.
- Persistence and UI consumers must interpret loosely defined data.
- Makes future contract evolution less predictable.
