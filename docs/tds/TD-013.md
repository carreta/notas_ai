# TD-013 — `develop` branch vs trunk-based integration

## Status

Proposed

## Context

The project needs a Git integration strategy that defines how developers integrate their work and how changes move toward the main/releasable codebase. The two main approaches considered are:

- A **`develop` branch workflow**, where feature branches are merged into `develop` and `main` represents a stable/released state.
- A **trunk-based workflow**, where developers integrate short-lived branches directly into `develop` (trunk), typically through pull requests and CI.

## Constraints

- All changes must go through code review before being integrated into the main codebase.
- CI must validate automated tests and static analysis before merging.
- The integration strategy should minimize merge conflicts and branch divergence.
- `main` should remain in a releasable state.

## Options considered

### Option A: `develop` branch

**Pros:**
- Familiar workflow for teams accustomed to Git Flow.
- Can be useful when multiple features need to be integrated and tested together before a release.
- Provides a clear conceptual separation between "development" and "released" code.

---

**Cons:**
- Introduces an additional long-lived branch and additional merge operations.
- Changes can remain in `develop` for longer periods, increasing branch divergence.
- Integration problems can be discovered later than they would be with direct trunk integration.
- Requires synchronization between `develop` and `main`.
- Can encourage larger pull requests and longer-lived feature branches.

### Option B: Trunk-based integration

**Pros:**
- Simpler branching model with fewer long-lived branches to maintain.
- Smaller and more frequent integrations reduce merge conflicts.
- Problems are detected closer to the change that introduced them.
- Keeps the team working against a single current version of the codebase.
- Encourages small pull requests and incremental delivery.

---

**Cons:**
- Requires reliable CI to prevent broken changes from entering `main`.
- Requires developers to keep feature branches relatively short-lived.
- Requires discipline around keeping `main` releasable.
- Teams unfamiliar with trunk-based development may initially find the workflow less intuitive.

## Decision

We choose trunk-based integration, the project will use `main` as the primary integration branch. Developers will work on short-lived feature branches and integrate changes through pull requests after code review and successful CI checks.

The project will rely on CI to maintain the quality of `main`. At minimum, the required checks should include:

- Automated tests.
- Static analysis.
- Any other project-specific quality checks established during development.

## Consequences

### Positive

- Simpler Git workflow with fewer long-lived branches. This reduces branch divergence and merge conflicts.
- Faster feedback when integrating changes.
- Smaller pull requests and more incremental changes are encouraged.
- `main` becomes the single source of truth for the current application state.

### Negative

- CI becomes a critical part of the development workflow.
- The team must maintain the discipline that `main` remains releasable.
- Developers need to keep feature branches short-lived.
