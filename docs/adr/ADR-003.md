# ADR-003 — Synchronous AI Analysis

## Status

Accepted

## Context

AI analysis may take significantly longer than normal application requests, particularly for large meeting transcripts or complex models. The application must determine whether AI analysis executes within the original HTTP request (synchronous) or is dispatched as an asynchronous background job.

This decision affects FR-003, FR-004, FR-005, FR-008, and the overall Phase 2 workflow. It is closely related to `TD-003` (AI timeout budget) and `TD-005` (retry/re-analysis behavior).

## Constraints

- The system must provide predictable behavior when AI processing takes longer than expected.
- AI failures must not corrupt or invalidate the original meeting record.
- The architecture should support retries or re-analysis if required by `TD-005`.
- The user must be able to determine whether analysis is pending, successful, or failed.
- The solution should remain manageable for Phase 2 infrastructure.
- The chosen execution model must be compatible with the provider-independent AI port (`TD-002`, `TD-009`).

## Options considered

### Option A — Synchronous AI analysis

Perform AI analysis within the same HTTP request that creates or submits the meeting.

**Pros:**

- Simple request/response flow.
- Immediate result available to the caller.
- Fewer infrastructure components.
- Easier initial implementation.

**Cons:**

- Request duration depends on AI provider latency.
- Greater risk of HTTP timeout.
- Poorer user experience for long meetings.
- Retries can be difficult to manage safely.
- Application workers remain occupied during AI processing.

### Option B — Asynchronous queue/job processing

Persist the meeting first and dispatch an AI analysis job to a queue.

**Pros:**

- Decouples meeting creation from AI latency.
- Better resilience to slow or temporarily unavailable providers.
- Natural support for retries.
- Easier to expose pending/failed/completed analysis states.

**Cons:**

- Requires queue infrastructure.
- Adds state management and operational complexity.
- Results are not immediately available.
- Requires additional testing for asynchronous workflows.

### Option C — Hybrid strategy

Use synchronous processing for small/fast requests and asynchronous processing when configured thresholds are exceeded.

**Pros:**

- Immediate results for simple cases.
- Avoids long synchronous requests for larger analyses.

**Cons:**

- More complex application behavior.
- Different execution paths need to be maintained and tested.
- User experience becomes less predictable.
- Threshold selection adds configuration.

## Decision

The team chose **Option A — Synchronous AI analysis**. AI analysis is performed within the same request that submits the validated meeting, keeping the flow simple and avoiding queue/job infrastructure for the current implementation.

This decision is recorded as `TD-004` (Approved: Option A).

## Relationship to the timeout

Synchronous execution is bounded by the fixed global AI analysis timeout defined in `TD-003`: **120 seconds**. A request that exceeds this budget produces the application-level `AI_TIMEOUT` failure and is never treated as a successful or partially valid analysis. The timeout prevents the synchronous request from occupying application resources indefinitely.

## Consequences

### Positive

- Simple, predictable request/response flow.
- No queue/worker infrastructure to operate for the MVP.
- Immediate result available to the caller.
- Easier initial implementation and testing.

### Negative

- Request duration depends on AI provider latency.
- Greater risk of HTTP timeout for long or complex meetings (mitigated by the 120s budget).
- Retries are harder to manage safely within a single request.
- Application workers are occupied during AI processing.

## Compatibility / migration

No queue or job infrastructure is introduced in the current implementation. The meeting is persisted with an explicit processing status (`VALIDATED` → `ANALYZING` → `COMPLETED` / `FAILED`) so the user can always observe analysis state. Controlled failures (including `AI_TIMEOUT`) are mapped to a failed state without corrupting the meeting record.

Asynchronous processing may be revisited later if production requirements (scale, long meetings, user experience) justify the added infrastructure; such a change would be captured by a new ADR that supersedes this one.
